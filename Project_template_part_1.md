# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**
- Пользователи могут:
  - включить отопление;
  - выключить отопление;
  - изменить значение температуры.
- Система поддерживает:
  - подключение новых устройств через специалистов компании.

**Мониторинг температуры:**
- Пользователи могут:
  - проверить значение температуры.
- Система поддерживает:
  - выполнение запросов о температуре от сервера к датчику.

### 2. Анализ архитектуры монолитного приложения

Архитектура приложения представляет из себя монолит на Java с СУБД Postgres.
Всё синхронно. 
Никаких асинхронных вызовов, микросервисов и реактивного взаимодействия в системе нет. 
Всё управление идёт от сервера к датчику. 
Данные о температуре также получаются через запрос от сервера к датчику.

### **4. Проблемы монолитного решения**

- имеет ограниченную функциональность: позволяет только управлять отоплением в доме и проверять температуру;
- отсутствует возможность самостоятельного подключения к датчику: каждая установка сопровождается выездом специалиста;
- синхронное взаимодействие при запросе данных от датчика - длительное время ожидания;
- СУБД Postgres может плохо справляется с объемом накопленных данных о показаниях, есть более подходящие решения.

# Задание 3. Разработка ER-диаграммы

Описание сущностией и атрибутов:

* Credentials - данные для аутентификации (могут быть заменены на использование AUTH-подсистемы)
  * cred_id — уникальный идентификатор учетной записи
  * user_id — идентификатор пользователя — внешний ключ к таблице User.
  * login — логин.
  * password — зашифрованный пароль.
* User - пользователь
  * user_id — уникальный идентификатор пользователя.
  * firstname — фамилия  пользователя.
  * name — имя  пользователя.
  * lastname — отчество пользователя.
  * email —  email пользователя.
  * phone —  телефон пользователя.
* House - дом
  * house_id — уникальный идентификатор помещения.
  * user_id —  идентификатор пользователя — внешний ключ к таблице User.
  * address — адрес помещения (не декомпозирован для хранения, так как не предполагается обработка пространственых данных).
* Module - модуль управления устройствами дома
  * module_id — уникальный идентификатор модуля управления (контрольная панель)
  * house_id — идентификатор помещения — внешний ключ к таблице House.
  * model — модель модуля.
  * name — наименование.
  * serial_number — серийный номер устройства.
* Settings - целевые значения контролируемых параметров модулем
  * module_id— уникальный идентификатор модуля управления (контрольная панель), внешний ключ к таблице Module, часть оставного первичного ключа.
  * device_id — уникальный идентификатор устройства, внешний ключ к таблице Device, часть оставного первичного ключа.
  * target_value — целевое значение контролируемго параметра (для упрощения считаем, что один датчик контролирует одно значение, в противном случае потребуется выделение еще одной сущности).
* Device - устройство
  * device_id — уникальный идентификатор устройства.
  * module_id — уникальный идентификатор модуля управления (контрольная панель).
  * house_id — идентификатор помещения — внешний ключ к таблице House (добавлен для быстроы фильтрации данных).
  * type_id — идентификатор типа устройства — внешний ключ к таблице DeviceType.
  * model — модель.
  * serial_number — серийный номер устройства.
  * status — текущее состояние устройства (включено/выключено).
  * frequenceMs - частота отброса телеметрии.
* DeviceType - тип устройства
  * type_id — уникальный идентификатор типа устройства.
  * type — тип устройства.
* TelemetryData - показания устройств на определенную дату
  * device_id — идентификатор устройства, часть состаного первичного ключа, внешний ключ к таблице Device.
  * datetime — дата фиксации показания, часть состаного первичного ключа. 
  * value — показания датчика.
  
* Описание связей:

 * User — House: один пользователь может иметь доступ к нескольким домам, но каждый дом связан только с одним пользователем.
 * House — Module: один дом может содержать один модуль управления, и каждый модуль принадлежит только одному дому.
 * Device — TelemetryData: одно устройство может генерировать множество записей телеметрии, но каждая запись принадлежит только одному устройству.
 * Device — DeviceType: одно устройство  может иметь только один тип, но каждый тип может быть связан только с 0 или более устройствами.
 * Module — Device: один модуль может управлять несколькими устройствами, и каждое устройство зарегистрировано только в одном модуле.
 * Module — Settings: один модуль может управлять несколькими параметрами (нескольких датчиков), и каждый параметр датчика управляется только в одном модуле.
 * Device — Settings: один датчик передает значения одного параметра, и каждый параметр датчика контролируется только одним модулем.
 * Credentials — User: один пользователь имеет одину учетную запись, одна учетная запись принадлежит одному пользователю.
